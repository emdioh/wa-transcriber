  (`ghcr.io/emdioh/wa-transcriber`, tags `v0.1.1`, `0.1.1`, `latest`).
  Compressed layer sizes from the release log: 9.1 MB amd64, 8.4 MB arm64,
  8.7 MB armv7 (the `docker image ls` size is about the 24 MB binary plus
  CA certificates; `docker image ls` reports 24.5 MB, under the 30 MB
  target). On amd64 the container starts as uid
  65532, `docker inspect` reports `healthy`, the setup page opens and the
  pairing QR is shown (owner check, 2026-11-20). Re-checked with Podman on
  amd64: a fresh volume is owned by 65532, the health probe reports
  `healthy`, the setup password, reply language, public URL and
  transcription settings all save, a real pairing survives a container
  restart (authenticated without a new QR), a voice note was transcribed
  through OpenRouter, `!reset` from WhatsApp re-executed the binary inside

  root-owned volume exits with the `chown` hint instead of starting. Still
  unverified: running the image on an arm64 or armv7 host. The local build context used to include
  `os/_output` (20 GB), which CI never saw; `.dockerignore` now excludes the
  Buildroot trees.
- The multi-arch image is private, like the repository. Pulling it needs a
  `ghcr.io` token with `read:packages`.
- Docker volumes first created by the pre-hardening image (root, `:80`) stay
  root-owned, and Docker never re-owns an existing volume. The binary now
  refuses to start in that case with `data directory /data is not writable`
  and the `chown` command to fix it, instead of starting a UI whose first
  save fails. A fresh volume gets uid 65532 from the image.
- The images themselves: both build and their partitions were inspected offline
  (contents, init scripts, binary present). The BeagleBone Black image was
  booted for the first time on 2026-11-20: the kernel console works on HDMI
  (and `earlycon` plus `console=tty1` were added for exactly that), but the
  binary looped on
  `open session db: failed to upgrade database: ... unable to open database
  file` because `/data` was never mounted: `S00boot` and `S01data` read the
  root device from `/proc/mounts`, which calls it `/dev/root`, and gave up.
  Both now resolve the device through `/sys/dev/block/<major>:<minor>`
  (shared `usr/lib/wat/sd.sh`, with a unit test in `make -C os check`), which
  fixes `/data` and, with it, `wat.txt` and the debug console. **Not yet
  re-flashed.** The runtime criteria in M6 and every scenario in M5b still
  need the boards.
  Two image bugs were fixed without hardware on 2026-11-20 and are equally
  unverified until booted: the FAT boot partition is now mounted read-only at
  `/boot` (before, `wat.txt` was never read, so the setup AP always used the
  `wa-setup-<MAC>` fallback and `country`/`hostname` did nothing), and the
  BeagleBone cmdline now uses `console=ttyS0,115200` instead of the pre-4.11
  `ttyO0`, and it boots with `earlycon` and `console=tty1` and without
  `quiet`, so the boot log appears on the serial header and on HDMI. The
  images also gained an opt-in debug console (`console=serial|usb|hdmi|all`
  in `wat.txt`); it is off by default and has never been exercised.
- The release workflow: it ran for `v0.1.0` and `v0.1.1`, producing the
  releases with three binaries and `SHA256SUMS` plus the multi-arch image;
  since `v0.1.1` it also logs the compressed size per platform.
- Italian bot replies: every reply has an Italian translation and unit tests
  exercise `!help`, `!status`, `!transcription`, `!t` and the error replies,
  but nobody has read them in a real chat yet.
- Everything in `internal/netmgr` beyond unit tests: the managed mode has never
  run on real hardware (no accessible network stack in the sandbox). The
  commands it issues are tested with scripted fakes only. Milestone **M5b**
  runs the on-device scenarios; see [hardware.md](hardware.md).
- Wired DHCP from a cold boot: fixed on 2026-11-21 without hardware
  (`internal/netmgr/linux.go`, regression test
  `TestManagedFirstPollDrivesEthernetWithCarrierDown`). The report "the BBB
  image has no DHCP client" was not a missing applet - both images carry
  `/sbin/udhcpc` (busybox applet), `/usr/share/udhcpc/default.script` and
  every command the script runs. The DHCP client never *ran*: the managed
  manager only acted on a false→true `carrier` transition, but a booted
  interface is administratively down and reads `carrier=0`, so
  `Ethernet.Up()` (`ip link set <if> up` + `udhcpc`) was never called and no
  transition could follow. The first poll now always runs the up path. The
  fix still has to be confirmed on a board by `make -C os bbb` (and
  `make -C os rpi2`) + flash (bead wat-f2z.7).
- Pairing on a board: **broken and fixed on 2026-11-21**, waiting for an
  on-board re-check (bead wat-f2z.8). The owner reported that scanning the QR
  made the phone answer "cannot pair". The board log shows why: the first
  attempt failed on DNS because the network was not up yet, the retry printed
  a QR at 10:40:25.019 and whatsmeow logged `Error sending close to websocket`
  363 ms later. The QR was already dead when the phone read it.
  Root cause is in the pairing loop, not in the network: `whatsmeow` registers
  an event handler per `GetQRChannel` and removes it only when that channel
  closes, so an attempt that fails after `GetQRChannel` (no network, DNS down,
  WhatsApp unreachable) leaves a handler behind whose context is already
  cancelled. The next attempt's QR event reaches it, its emitter takes the
  context-done branch and calls `client.Disconnect()`: the socket dies right
  after the code is shown, the disconnect is *expected* so there is no event
  and no auto-reconnect, and the stale code sits on screen until its 60 s
  timeout. Reproduced on amd64 without a phone: old loop, QR at +0.00 s and
  `connected=false` from +0.03 s on, forever; fixed loop, `connected=true` for
  the whole run. The fix caches one QR channel per pairing session
  (`qrChanCache`), so a failed attempt reuses it instead of registering a
  second handler; unit tests cover reuse, error paths and cancellation. This
  bug also hid the wired-DHCP fix above, which was never confirmed because no
  pairing could complete.
  Found while diagnosing, not fixed: `Ethernet.Down()` flushes the interface
  address on every carrier loss, which kills live sockets (wat-f2z.9); the
  first pairing attempt runs before a usable resolver exists (wat-f2z.10);
  the mDNS responder joined its group twice and renamed itself to
  `wa-2.local` (wat-f2z.11).

## Known limitations and accepted issues

- **`!status` links are not clickable**: WhatsApp does not linkify
  `http://<ip>:<port>/`. URLs are shown as inline code so they can be copied
  with a long press. Accepted. (A `nip.io` hostname was considered and
  rejected: external DNS dependency, blocked by DNS-rebinding protection on
  many routers, leaks the LAN IP.)
- The web UI is plain HTTP (no domain for a certificate). Do not expose it
  to the Internet.
- Until a password is set, whoever opens the UI first sets it. Set it right
  away (or with `!password` from WhatsApp).
- Logs are lost on restart (RAM only, by design).
- The debug console in `wat.txt` (`console=off|serial|usb|hdmi|both|all`) logs
  in as root with an empty password: it is a physical-access debugging aid,
  not a feature. The images currently ship `console=all` so the boards can be
  debugged over HDMI, USB or the UART header; set `console=off` before a
  device goes anywhere a stranger can reach a port.
- Bot replies exist in English and Italian (System page). A new reply needs
  both entries: `TestMessagesComplete` fails otherwise.
- With two transcribers in one chat, both answer only until the M2 result
  allows claims to be turned on (`-coord-claims`). In observe-only mode the
  duplicate is accepted by design.
- One WhatsApp account per device.

## Code map

```
cmd/wa-transcriber/main.go   flags, wiring, reset/unlink/re-exec, memory limit
internal/wa/                 whatsmeow client, pairing, event conversion, sending
internal/bot/                commands, voice dispatch, !status text
internal/transcribe/         settings resolution, providers, translation, queue
internal/web/                server, sessions, pages, templates/, static/
internal/config/             config.json store
internal/coord/              multi-transcriber coordination (claims, watchdog)
internal/netmgr/             network manager: none + managed (ethernet, WiFi, AP, policy)
internal/watchdog/           hardware watchdog keeper (images only)
internal/netmgr/mdns/        in-binary mDNS responder for wa.local
internal/status/             runtime state, interface addresses
internal/logbuf/             RAM log buffer
os/                          Buildroot BR2_EXTERNAL tree (Pi 2, BeagleBone Black)
docs/                        ARCHITECTURE.md, STATUS.md, PLAN.md, hardware.md
```

Build and test: `make test`, `make build`, `make dist`, `make -C os check`. Run locally:
`./wa-transcriber -data ./data -listen :8080`. Network management is off
unless `-network managed` (needs root).
