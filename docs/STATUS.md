## Init mode (D19): code done, needs one board test

The BeagleBone Black (`os/board/bbb/extlinux.conf`), Cubieboard 1
(`os/board/cubie/extlinux.conf`) and Raspberry Pi 1/2
(`os/board/rpi1/cmdline.txt`, `os/board/rpi2/cmdline.txt`) images now boot with
`init=/usr/bin/wa-transcriber`: the kernel execs the transcriber instead of
busybox init, and `internal/boot` does the mounts, the hostname, the watchdog
module, USB WiFi modalias coldplug + hotplug registration, `/boot/wat-migrate`
eMMC migration, and the `/data` partition that the
`S00boot`/`S01data`/`S10mdev`/`S90watchdog` scripts used to do. `internal/sntp`
replaces busybox `ntpd` in init mode. There is no inittab, no `rcS` and no shell
in the boot path.

Verified here, without a board:

- `internal/boot` and `internal/proc` unit tests (mount decisions, idempotency
  on a re-exec, the `DATA` label rules, the first-boot `sfdisk`+`mkfs.ext4`
  path, `e2fsck` once after a failed mount, and that the sweep never takes a
  child `os/exec` is waiting for);
- the normal path is unchanged: the container image still comes up in setup
  mode and answers `200` on `/healthz` (Podman, amd64), and `-init` in a
  container without mount rights fails loudly and stays alive waiting for the
  watchdog instead of dying with a kernel panic;
- the debug console is ported too (`console=` in `wat.txt`): the CDC-ACM
  gadget is created through configfs by the program, so flipping `init=` does
  not take away the only way onto a board without a keyboard.

Not verified: **the real boot on the board** (mounts, `sfdisk` on the card,
the reaped orphans of the WiFi daemons). Two attempts were made on the
owner's SD card on 2026-11-25 and both found bugs before the boot path could
be judged: the first died because the "am I init" check read `/proc/cmdline`
before `/proc` was mounted (fixed: `InitRequested` mounts `/proc` itself),
the second was cut short by that card failing at the mmc layer (`error -110`,
`Journal has aborted` on `/data`). The mode now falls back to `/sbin/init`
when `Setup` fails, so a bad attempt boots the old path with a console
instead of needing a card reader. That needs the owner: flash a card
built from this tree, watch the serial console, and check `mount`, `cat
/proc/1/cmdline`, the web UI and a pairing. Rollback is deleting `init=` from
`extlinux.conf` on the boot partition.

Still open, in this order: verify the real boot on the boards (`wat-b14.1` for
BBB, plus Pi 1/2), and then drop busybox init and the legacy init scripts once
every board boots as init (`wat-b14.4`, deciding what becomes of the opt-in
`console=` shell). Closed on `kernelwa`: `wat-b14.2` (`internal/sntp`),
`wat-b14.3` (Pi `cmdline.txt`), `wat-b14.5` (USB WiFi coldplug/hotplug),
`wat-b14.6` (`/boot/wat-migrate` eMMC migration), `wat-b14.7` (`proc.SetLogger`
race & log format), `wat-b14.8` (re-exec idempotent USB gadget UDC & getty).

## M9 update flow on the BeagleBone Black (2026-11-22, agent over the serial console)

  `v0.2.0 is available` in the System page.
- **Install**: 24 MB asset downloaded (≈12 s), sha256 + `EM_ARM` + size checked,
  staged as `pending`, `syscall.Exec` of the bootstrap, promoted, running
  `v0.2.0`; `verified: true` 60 s later. The state file went from
  `{active: nil}` to `{active: v0.2.0, verified: true}`.

  (`tries` 1, 2, 3 — a WARN in the log each time), then rolled back to

  `v0.2.0`.

## Known limitations and accepted issues

- **`!status` links are not clickable**: WhatsApp does not linkify
  `http://<ip>:<port>/`. URLs are shown as inline code so they can be copied
  with a long press. Accepted. (A `nip.io` hostname was considered and
  rejected: external DNS dependency, blocked by DNS-rebinding protection on
  many routers, leaks the LAN IP.)
- The web UI is plain HTTP (no domain for a certificate). Do not expose it
  to the Internet.
- Until a password is set, whoever opens the UI first sets it. Set it right
  away (or with `!password` from WhatsApp).
- Logs are lost on restart (RAM only, by design).
- The debug console in `wat.txt` (`console=off|serial|usb|hdmi|both|all`) logs
  in as root with an empty password: it is a physical-access debugging aid,
  not a feature. The images currently ship `console=all` so the boards can be
  debugged over HDMI, USB or the UART header; set `console=off` before a
  device goes anywhere a stranger can reach a port.
- Bot replies exist in English and Italian (System page). A new reply needs
  both entries: `TestMessagesComplete` fails otherwise.
- With two transcribers in one chat, both answer only until the M2 result
  allows claims to be turned on (`-coord-claims`). In observe-only mode the
  duplicate is accepted by design.
- One WhatsApp account per device.
- WiFi hardware: the setup AP needs an adapter with `NL80211_IFTYPE_AP`. An
  RT5370 (`rt2800usb`) needs no firmware at all; an MT7612U (`mt76x2u`) now
  works because the images ship `mt7662*.bin` (before 2026-11-23 they did
  not, so it failed on the missing blob). Realtek 8188/8192 dongles
  (`rtl8xxxu`) are **client only** in Linux 6.1 — the driver advertises no AP
  mode, so such a dongle can join a network but cannot serve the setup AP.
  Details and the observed dongle: [hardware.md](hardware.md) §1.1.

## mDNS: fix for `wa.local` not resolving (2026-11-21, awaiting on-board check)

The owner could not reach `wa.local` from an Android phone. Android does
support `.local`: the DNS resolver gained one-shot mDNS queries (RFC 6762
section 5.1) with the Google Play System Update of November 2021 (Google issue
140786115, "Fixed"), so Android 12+ resolves `.local` and Android 13 has it
natively; older versions only offer `NsdManager` service discovery, where a
`.local` name in a browser never resolves. Here the device was the problem:

- **Renamed itself on its own address.** `OtherAddress` matched any `A` record
  for the configured name, so an announcement carrying *our* address counted
  as a conflict. Our own announcements return on the same socket
  (`SetMulticastLoopback(true)`), and the owner's LAN also has an mDNS
  reflector at 192.168.1.254 that answers `wa.local` LAN-wide. The board log
  shows the result: `mdns: name conflict, renamed old=wa.local new=wa-2.local
  ip=192.168.15.43` — the IP is the board's own. After the rename nothing
  answers `wa.local`, which is exactly the reported symptom. Confirmed with a
  unit test before fixing: `OtherAddress` on our own announcement packet
  returns our own address.
- **Unicast queries were never received.** The socket came from
  `net.ListenMulticastUDP` bound to the group address, so only packets
  addressed to 224.0.0.251 arrived; a query sent straight to the device
  (RFC 6762 section 6.7, which some resolvers use) was dropped. Measured from
  the dev box: direct query to 192.168.15.43:5353 got no answer, while a
  multicast query was answered only by the reflector, not by the board.
- **Join group failed with EADDRINUSE.** `ListenMulticastUDP` already joins
  the group, and the explicit per-interface `JoinGroup` then failed; the
  code logged it and never joined that interface, so a Wi-Fi interface
  appearing later was never joined either.

- **One-shot replies were not conventional.** A query from a source port other
  than 5353 comes from a "simple resolver" doing one-shot lookups, and RFC 6762
  section 6.7 requires the reply to look like a common DNS answer: the query ID
  repeated, the question repeated, no cache-flush bit, TTL at most 10 s. The
  responder sent ID 0, no question, cache-flush set and TTL 120, which a
  resolver like Android's may well discard. The mDNS reflector on the owner's
  LAN does it right, which is presumably why the name resolved from a laptop
  and not from the phone.

Fixes: one socket bound to the wildcard address joining the group per
interface (like avahi), joining interfaces that appear later, answering
unicast queries too, conventional one-shot replies, and renaming only when the
conflicting record names a different address. Unit tests:
`TestOwnAnnouncementIsNotAConflict`, `TestLocalIPFor`, `TestIsMulticast`,
`TestLegacyUnicastResponseFormat`, `TestMulticastResponseKeepsMDNSForm`,
`TestIsLegacySource`.

`v0.1.1-26-g67f9c3e`): `udp 0.0.0.0:5353` is bound, a query sent straight to
192.168.15.43:5353 is answered (it was silent before), a multicast one-shot
query gets two answers, the board's own with `class 0x8001`, ID echoed and
TTL 10, and `wa-2.local` does not exist, so the device no longer renames

binary swaps (`/data/session.db` intact, one ESTABLISHED socket to WhatsApp).
